01Intro

InstaDeep needed one visual and behavioural language across its product surfaces. I built the design system that provides it, and I still own it.

It covers the usual ground — components, type, colour, spacing — and then the part most systems leave undefined: how things move.

02Browse the system

The system is a working library rather than a document. What follows is one component taken end to end — the button — because depth shows more than a gallery would: every variant and state, the values behind each one, and the rules for when to reach for which.

03The patterns, running

The system itself is internal, so what follows is not an export of it. These are the interaction and motion patterns I specify, rebuilt here as working components in this site's own tokens.

That distinction matters, and it is also the point: motion cannot be shown in a screenshot. "180ms, ease-out, a 4px rise" is a claim until you can watch it happen. Each demo below runs the timing printed beside it, so the documentation and the behaviour are the same thing.

Button

Four states. The press is the important one — a 60ms scale to 0.97 makes a click feel received rather than merely registered.

hover 160ms · press 60ms · cubic-bezier(.22,1,.36,1)

Input field

The label moves rather than disappears, so the field never loses its name. Error state animates in with the message so the change is noticed without being alarming.

label 180ms · error shake 240ms

Toggle

The knob leads and the track colour follows slightly behind, which reads as the switch causing the state rather than both changing at once.

knob 200ms spring · track 260ms

Toast

Enters from below with a short rise, holds, then leaves by fading and dropping. Entrance is faster than exit — arrivals should be noticed, departures should not.

04Motion and interaction, not just components

A component library tells you what a button looks like. It rarely tells you how it enters, what it does while it waits, or how it answers a click. Those decisions get made ad hoc, screen by screen, and that is why products drift into feeling assembled rather than designed.

I specified the motion and interaction centrally alongside the components, so timing and behaviour are decided once and inherited everywhere.

05The outcome

The system is used across InstaDeep and in every demo the company gives.

That is the measure I would point to. A design system justifies itself by the time it removes: demos that used to need assembling now start from something that already exists and already behaves correctly. Nobody notices a system that is doing its job — they notice the week it gives back.
